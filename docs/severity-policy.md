# TMS 결함 심각도 정책 — 제안 v1

상태: **합성 데모를 위한 검토 가능한 초안**. 실제 고객 피해나 운영 사고로 보정한 표준이 아닙니다.
정책 ID는 `tms-severity-proposal-v1`, 실행 규칙은 [`tms/severity.py`](../tms/severity.py)에 있습니다.
심각도는 고객 영향, 우선순위는 처리 일정입니다. `priority`는 심각도와 출시 판정에 영향을 주지 않습니다.

## 분류 순서와 기준

다음 순서로 검사합니다. 단순히 작은 숫자가 입력됐다는 이유로 심각도를 신뢰하지 않습니다.

| 분류 | 충족 조건 | 가상 예시 | 게이트 연결 |
| --- | --- | --- | --- |
| S1 치명적 | 확인된 데이터 유실·보안 침해·잘못된 금전 처리 중 하나. 또는 핵심 업무를 완료할 수 없고 검증된 우회 방법도 없음 | 다른 사용자 정보 노출, 결제 중복 처리, 전체 조회 기능 불가 및 우회 없음 | 기존 엔진 P1로 변환; 미해결이면 NO_GO |
| S2 주요 | S1 조건이 없고, 주요 기능 손상 또는 검증된 우회가 있는 핵심 업무 차단 | 경고 필터가 전체 행을 반환; 전체 목록에서 확인하는 우회가 검증됨 | P2로 변환; 최소 조건부 대상 |
| S3 경미 | 주요·핵심 기능 영향과 데이터·보안·금전 피해가 없고, 영향이 경미한 표시·사용성 문제에 한정됨 | 업무를 막지 않는 설명 문구 오류 | P3로 변환; 잔여 점수에 기여 |
| UNCLASSIFIED | 근거 누락, 알 수 없는 영향, 모순된 입력, 확인 가능한 분류 없음 | 데이터 유실 여부를 아직 조사하지 못함 | 등급을 추정하지 않고 EVIDENCE_INSUFFICIENT |

낮은 재현 빈도·적은 사용자 수·낮은 처리 우선순위는 확인된 S1 피해를 낮추지 않습니다.
데이터/보안/금전 피해 또는 우회 없는 핵심 업무 차단이 확인됐다면 다른 영향 필드가 미확인이어도 S1입니다.
S2/S3를 판단할 때는 모든 영향 필드와 사용자 범위가 확인되어야 합니다.
`minor_only=true`와 주요/핵심 영향 선언은 모순입니다.

## 분류에 필요한 근거

결함마다 ID·제목·open/resolved 상태, 영향 필드, 범위, 증적, 분류자와 사유를 기록합니다.

| 필드 | 의미 |
| --- | --- |
| `data_loss` | 데이터 유실이 확인됐는가 |
| `security_violation` | 정보 노출·권한 침해 등 보안 피해가 확인됐는가 |
| `incorrect_financial_effect` | 잘못된 금액·중복 청구 등 금전 처리가 확인됐는가 |
| `core_journey_blocked` | 사전에 지정한 핵심 업무를 완료하지 못하는가 |
| `workaround_verified` | 피해를 피하면서 업무를 완료하는 우회 방법을 실제로 확인했는가 |
| `major_function_impacted` | 주요 기능의 결과가 요구사항과 다르거나 사용이 차단되는가 |
| `minor_only` | 영향이 경미한 표시·사용성 문제에만 한정되는가 |
| `affected_scope` | all / subset / single / unknown; 개수만으로 심각도를 낮추지 않음 |
| `evidence_refs` | 해당 실행의 실제 합성 증적 경로 |
| `assessed_by`, `assessment_note` | 분류자와 판단 근거. 데모에서는 가상 분류자 |

영향 필드는 boolean 또는 미확인을 뜻하는 `null`입니다. 문자열 `"false"`는 거절합니다.
증적·분류자·사유가 없으면 분류 미완료입니다. 증적은 실행 폴더 안에 있고 저장된 해시와 일치해야 합니다.
알고리즘이 제품 피해를 스스로 발견하지는 않습니다. 사람이 확인한 사실과 역할·권한 검증이 실제 적용에 필요합니다.

## 테스트 중요도와 결함 심각도

`criticality`는 실행 전 정한 사용자 흐름의 중요도, `severity`는 실제로 확인된 피해입니다.
전체 알림 조회는 critical, 경고 필터는 high로 사전에 지정했습니다. 제품별 핵심 업무 목록은 별도 검토가 필요합니다.
기존 게이트의 확인된 critical 제품 실패 NO_GO 조건을 유지하므로, S2로 분류해도 critical 실패를 면제하지 못합니다.

모든 선언 Baseline/Target 결과가 최신·동일 후보/환경·증적 보유·검수 승인 상태여야 위험 점수를 계산합니다.
분류 미완료가 있으면 점수는 0이 아니라 `null`입니다. 다른 확인된 S1 등 hard blocker가 있으면 NO_GO를 유지하고 증거 부족도 함께 표시합니다.

## 잔여 위험과 조건부 수용

기존 공개 엔진 제안 정책을 사용합니다: P2 15, P3 5, high/medium/low 제품 실패 12/6/3, flaky 5.
20점 미만이 GO의 점수 구간, 20–44는 조건부, 45 이상은 NO_GO입니다.
S2·제품 실패·flaky는 점수와 관계없이 최소 조건부 대상입니다.
조건부에는 담당자·보강 조치·만료 시각이 있는 유효한 수용 기록이 필요하고, 없으면 NO_GO입니다.
엄격 모드는 조건부도 종료 코드 3으로 보류합니다. QA/운영 승인·롤백 테스트·모니터링 담당자·롤백 기준도 필수입니다.

점수는 확률이 아니며 아직 운영 데이터로 보정되지 않았습니다. 같은 원인의 결함과 테스트 실패가 함께 가산될 수 있습니다.
새 conditional 실행은 S2/P2 15 + high 실패 12 = 27점입니다.
이전 공개 JSON conditional 예시는 테스트 통과 + P2만 있어 15점으로, 서로 다른 시나리오입니다.
자세한 규칙은 [통합된 게이트 정책](../modules/release_gate/docs/workflow-quality-gate-policy.md)에 있습니다.
