## 1. 공유 결과 화면의 정보 구조

### 문제

공유 링크에서 절차와 증적을 세로로 나열하면 사용자가 화면을 오가며 대응 관계를 찾아야 합니다. 원본 시스템의 복잡한 작업 화면을 그대로 공유할 필요도 없었습니다.

### 구현

- 테스트케이스별 카드 안에서 증적과 사전조건·절차·기대결과·판정을 나란히 배치.
- 증적 썸네일, 이전·다음 이미지 전환, 원본 크기 확대 제공.
- 키보드 닫기와 기존 요소로의 포커스 복귀 지원.
- 라이트·다크 테마와 PC·노트북 폭 대응.
- 공유된 결과와 이미지 범위 유지, 출력 문자열 이스케이프, 스크립트 해시 기반 허용.

### 검증

렌더링·출력 검사 3건과 PC 폭 4종 × 테마 2종을 확인했습니다. 실제 공유 결과에 이미지가 한 장인 경우와 별도 두 장 fixture를 구분해 확대와 전환을 검사했습니다.

### 설계 판단

외부 독자는 결과의 근거를 빠르게 확인하는 것이 목적이므로 검수 버튼을 공유 화면에 넣지 않았습니다. 기존 댓글 게시 형식과 결과 저장 계약을 유지하면서 링크로 여는 화면의 정보 구조를 바꿨습니다.

## 2. 이슈 본문 조회 실패와 재시도

### 문제

목록에서 제목은 확보했지만 상세 조회가 실패한 경우, 본문이 원래 없는 것처럼 보일 수 있었습니다. 제목만 있는 상태에서 분석을 시작하면 입력 근거도 불명확해집니다.

### 구현

본문 조회 실패 상태를 별도로 관리하고 다음 동작을 제공합니다.

1. 본문을 불러오지 못했다는 안내.
2. 본문 다시 불러오기 버튼.
3. 필요한 사람만 펼쳐 볼 수 있는 상세 오류.
4. 본문 확인 전 분석 시작 제한.

### 검증

가짜 API로 실패 응답과 정상 응답을 순서대로 제공해 `실패 안내 → 다시 불러오기 → 본문 표시`를 확인했습니다. 두 제품의 이슈·런 화면 이동과 복귀, PC 폭·테마도 검사했습니다.

이 과정에서 테스트가 JavaScript 모듈의 경로까지 API로 가로채는 문제를 발견했습니다. 요청 가로채기 범위를 서버의 API 경로로 좁혀, 화면 코드 로딩과 테스트 응답을 구분했습니다.

### 설계 판단

제품의 오류와 테스트 도구의 오류를 따로 분석해야 회귀 검사가 신뢰할 만한 근거가 됩니다. 단순히 대기 시간을 늘리는 대신 실제로 어떤 요청이 대체되고 있는지 확인했습니다.

## 3. AI 지원과 코드 기반 판정의 역할 분리

### 문제

AI가 테스트케이스나 코드를 작성했다는 사실만으로 요구사항이 검증되었다고 볼 수 없습니다. 실행 환경과 데이터가 부족한 경우까지 통과로 기록하면 결과의 신뢰성이 떨어집니다.

### 구성

| 단계 | 담당 역할 | 남기는 근거 |
|---|---|---|
| 분석·초안 | AI 지원 + 사람의 범위·제약 설정 | 이슈·소스 근거, 절차·기대결과 |
| 코드 작성 | AI 지원 + 코드 검토·정적 검사 | TC와 자동화 연결 |
| 반복 실행 | 자동화 코드 | assertion, 요청응답, 관찰값 |
| 결과 저장 | 실행·발행 코드 | 판정, 버전, 해시, 증적 |
| 검수 | 사람 | 검수 결정과 메모 |

### 설계 판단

작성 완료·실행 완료·검수 완료를 별도 상태로 관리합니다. 실패를 제품 결함, 자동화 오류, 환경 문제, 데이터 부족 등으로 분류하고 미실행·미확인을 통과로 바꾸지 않습니다.

이 사례는 프로젝트의 역할 분리와 운영 원칙을 설명합니다. 모든 메뉴의 자동화·실행·검수가 완료되었다는 의미는 아닙니다.
