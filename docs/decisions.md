# 설계 결정과 비용

[프로젝트 소개로 돌아가기](../README.md)

## API와 작업 실행기를 분리

**이유:** 분석·자동화 작성·테스트 실행은 일반 조회 요청보다 오래 걸립니다. API 재시작과 작업 실행의 영향을 분리할 필요가 있었습니다.

**선택:** API는 작업을 접수하고 실행기는 대기 작업을 처리하도록 구성했습니다.

**비용:** 작업 상태, 실행 주체, 중단·복구 처리가 추가로 필요합니다. 별도 프로세스가 있다는 것만으로 모든 장애 복구가 보장되지는 않습니다.

## 실행 당시 문서를 보존

**이유:** 테스트케이스가 수정된 뒤 과거 결과에 현재 문서만 표시하면 당시 검증 범위를 오해할 수 있습니다.

**선택:** 실행 당시 내용과 코드 해시, 제품 버전, 결과·증적을 연결합니다.

**비용:** 기록의 크기와 버전 관리 부담이 늘어납니다. 대신 결과를 나중에 검토할 때 어떤 근거를 사용할지 명확해집니다.

## 자동 판정과 사람 검수를 분리

**이유:** 자동화가 통과한 것과 담당자가 결과·증적을 검수한 것은 서로 다른 사건입니다.

**선택:** 두 상태를 별도로 관리하고, 게시 조건을 확인합니다.

**비용:** 상태 표시와 필터·게시 로직이 복잡해집니다. 완료의 의미를 분명하게 보여주는 UI가 필요합니다.

## 읽기 전용 공유 결과를 별도로 제공

**이유:** 결과를 받는 사람에게 운영·관리 기능 전체가 필요한 것은 아닙니다.

**선택:** 게시한 결과 범위의 절차·판정·증적을 보여주는 별도 화면을 제공합니다.

**비용:** 공유 범위와 접근 경계, 화면 출력 처리를 별도로 유지해야 합니다.

## 반복 회귀는 코드로 수행

**이유:** 반복 실행마다 AI의 자연어 판단만으로 PASS·FAIL을 결정하면 판정 근거의 일관성을 관리하기 어렵습니다.

**선택:** AI를 분석·작성·실패 수리에 활용하고 반복 검증은 코드의 조건 비교로 수행합니다.

**비용:** assertion과 fixture를 관리해야 합니다. 테스트 코드도 오류가 날 수 있으므로 실패 원인을 제품과 자동화로 구분합니다.
